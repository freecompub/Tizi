# Notes — Jeff Patton, User Story Mapping (O'Reilly, 2014), 324 p.
## Tranche 1 (avant-propos, préface)
- Fowler : le découpage en stories fait perdre la vue d'ensemble ; la carte donne le « big picture » ; les stories servent à susciter la conversation, pas une communication à sens unique analyste → développeurs ; les programmeurs doivent participer à cadrer.
- Cooper : construire une fonction à la fois est une bonne méthode de construction mais une mauvaise méthode de conception (« Frankenstein ») ; la carte garde la structure narrative tout en permettant le découpage.
- Cagan : bonnes équipes = vision, essais rapides d'idées, ingénieurs qui voient les prototypes tous les jours (pas seulement en sprint planning pour estimer), contact client hebdomadaire, beaucoup d'idées échouent, instrumentation, célèbrent l'impact sur les KPI plutôt que la livraison.
- Préface : pièges — perdre la vue d'ensemble ; ne pas savoir quand on aura fini ; « conversation » prétexte à ne rien écrire puis oublier ; critères d'acceptation écrits sans compréhension partagée → l'équipe ne finit pas ; « pas d'utilisateurs donc pas de user stories ». Les stories ne sont pas un moyen d'écrire de meilleures exigences mais d'avoir de meilleures conversations.
## Tranche 2 (Read This First, ch. 1 début)
- Organisation : ch. 1-4 vue d'ensemble ; 5 exercice ; 6-12 stories ; 13-15 cycle de vie (opportunités → découverte → backlog viable) ; 16-18 livraison sprint par sprint.
- Deux idées clés : le but des stories n'est pas d'écrire de meilleures stories ; le but du développement produit n'est pas de faire des produits.
- **Documents partagés ≠ compréhension partagée.** On externalise (dessins, cartes) pour découvrir qu'on comprenait différemment. Arrêter de chercher le document parfait ; écrire quelque chose puis converser avec mots et images.
- Documents = photos de vacances : ne parlent qu'à ceux qui étaient là. Documenter pour se souvenir ; photographier, filmer les résultats des conversations. Si une seule personne tape dans un outil pendant que les autres parlent, c'est mal fait.
- Modèle « maintenant / plus tard » : idée → output → **outcome** (ce que les gens font différemment) → **impact** (effet à long terme pour l'organisation). Mesurer l'outcome, pas les fonctions livrées.
- Bonnes conversations de stories : **qui et pourquoi**, pas seulement quoi.
- **Minimiser l'output, maximiser outcome et impact** ; « build less ». Distinguer acheteurs (choosers) et utilisateurs.
- « Requirements » = souvent « tais-toi » : coupe la conversation sur les gens et le problème. Une fraction de ce qui est « requis » peut suffire.
- Stories ≠ exigences écrites ; discussions menant à des accords sur quoi construire.
- Ch. 1 : stories nommées d'après leur usage (raconter), pas ce qu'on écrit. Carte = pattern. « Les story maps servent à décomposer les grandes stories en les racontant. » Tragédie du backlog plat (Gary, Mad Mimi) : liste priorisée, construction pièce par pièce, perte de vision et de budget. « Talk and doc » : écrire les points clés sur des cartes pendant qu'on parle.
## Tranche 3 (ch. 1 fin, ch. 2 début)
- Penser–écrire–expliquer–placer : écrire l'idée avant de l'expliquer ; noter ses idées pour continuer d'écouter.
- Ordre de la conversation avec Gary : 1) **cadrer** (objectifs, bénéfices, problèmes ; ordonner les objectifs en les déplaçant), 2) **clients et utilisateurs** (types, bénéfices ; choisir UN utilisateur à ravir d'abord ; différer certains types avant tout détail), 3) **raconter la journée d'un utilisateur** de gauche à droite (ordre = séquence ; dessus/dessous = priorité ou décomposition), 4) **détails et options**.
- « Mile wide, inch deep » : aller au bout de l'histoire avant les détails.
- La carte fait apparaître les trous dans sa propre pensée ; l'histoire traverse plusieurs utilisateurs (manager, fan, salle).
- Cartes = phrases verbales courtes (« démarrer une promotion ») ; « et puis » entre colonnes, « ou il pourrait » entre détails.
- Questions par étape : que font-ils précisément ? alternatives ? qu'est-ce qui rendrait cela formidable ? que se passe-t-il quand ça se passe mal ?
- Autour de la carte : objectifs, clients/utilisateurs, croquis d'IHM.
- Gary : presque rien de ce qu'il avait construit (backlog plat) n'était sur la carte.
- Encadré TLC (école d'art) : la colonne vertébrale fait voir le processus métier commun ; lexique commun (« Classes » renommé « Delivery ») ; priorisation binaire « on ne peut pas démarrer sans » au-dessus de la ligne, plutôt que MoSCoW.
- Ch. 2 : « il y a toujours plus à construire que de gens, de temps ou d'argent ». Globo : 8 équipes construisent UNE carte d'une release commune pour voir les dépendances ; colonne vertébrale (backbone) à plusieurs niveaux (« grandes choses et petites choses ») ; flux narratif traversant plusieurs utilisateurs et systèmes ; personas au-dessus ; anthropomorphiser les systèmes.
- Jeu du « What-About » ; **le périmètre ne dérive pas, la compréhension grandit.**
- Se focaliser sur ce qui se passe hors du système pour décider ce qui est dans le système. Trancher (slices) horizontalement par ruban ; MVP = ce dont les utilisateurs ont besoin pour l'outcome visé (élections brésiliennes).
- **Roadmap de releases** : à gauche de chaque tranche, l'intention / l'outcome visé ; la liste des releases est une liste de bénéfices, pas de fonctions.
- **Prioriser les outcomes, pas les fonctions** ; sans outcome cible, prioriser est presque impossible. Choisir pour qui on change le monde (et qui on laisse de côté).
- Encadré SEP : modèle de priorisation différenciateur / spoiler / réducteur de coût / mise de table (table stakes).
## Tranche 4 (ch. 2 fin, ch. 3, ch. 4 début)
- SEP : couleurs par catégorie, désaccords révélés (le différenciateur de l'un est la mise de table de l'autre), vote ; économies avant toute ligne de code.
- MVP — mauvaise définition : le produit le plus médiocre qu'on puisse livrer. Bonne : **plus petite release qui atteint les outcomes visés** ; « minimum » est subjectif → préciser pour qui ; préférer « minimum viable solution ». On ne fait que deviner : trop bas = échec, trop haut = trop cher.
- 3e définition (Ries) : plus petite chose à faire pour prouver ou réfuter une hypothèse → **MVPe** (expérience).
- Questions clés : quelles sont nos hypothèses les plus grandes et les plus risquées ? comment remplacer un risque par de l'information ?
- Ch. 3 (Eric, Liquidnet) : 1re discussion = **cadrer l'opportunité** (grande idée, clients/acheteurs, utilisateurs, pourquoi ils la voudraient, pourquoi nous la construisons) ; **valider que le problème existe** (parler aux clients, constituer un vivier de « partenaires de développement ») ; prototyper (scénarios, maquettes, prototype haute fidélité) et tester ; se méfier de ce que les gens disent vouloir ; **construire pour apprendre** : livrer moins que minimal aux partenaires, mesurer l'usage réel (métriques), parler avec eux.
- Backlog d'Eric = story map : backbone stable, tranche du haut = release en cours (2 sprints), à gauche de chaque tranche son **objectif d'apprentissage** ; les cartes du haut partent vers un **tableau de tâches** du sprint ; la tranche en cours est **deux fois plus épaisse** pour prioriser après découpage ; quand une release part, on remonte la tranche suivante et on refait What-About et découpage.
- Itérer jusqu'au viable : jusqu'à ce que les partenaires utilisent en routine et recommandent (clients de référence) ; alors seulement vendre.
- Kniberg skateboard → voiture : chaque release utilisable ; **chaque release est une expérience : savoir ce qu'on veut apprendre** ; focaliser sur un segment.
- Découverte produit (Cagan) : apprendre aussi vite que possible si on construit la bonne chose ; ce qu'on construit tôt n'est pas forcément prêt pour la production (base en mémoire).
- Ch. 4 (Workiva) : découverte en ~3 jours (cadrage, validation client, prototypes Axure testés à distance) ; **cartographier seulement ce qui sert la conversation** (une fonctionnalité suffit).
- Raconter la carte à l'équipe avec les écrans imprimés ; l'équipe trouve des dépendances techniques et des détails oubliés.
- **Les meilleures estimations viennent de développeurs qui comprennent vraiment ce qu'ils estiment.**
- Plan de développement en 3 tranches : 1) **walking skeleton fonctionnel** (Cockburn ; « steel thread », « tracer bullet ») de bout en bout pour lever les risques techniques ; 2) étoffer vers le livrable (découvrir les imprévus prévisibles) ; 3) affiner/polir. **Ne pas livrer chaque tranche** : jalons internes avec objectifs d'apprentissage ; ne pas calquer tranches = sprints.
- Une estimation est estimée ; mesurer souvent rend meilleur à prédire ; petites tranches = plus de mesures. Le PO traite les estimations comme un **budget de livraison**.
## Tranche 5 (ch. 4 fin, ch. 5)
- Gérer le budget : mesurer chaque petit morceau construit comme une dépense ; à mi-temps mais au tiers du travail → emprunter du budget, simplifier sans perdre le bénéfice, ou renégocier. Attaquer tôt ce qui peut faire exploser le budget (le risqué), repéré avec toute l'équipe.
- Encadré SEP : **Risk Stories** dans la carte (ce que l'équipe doit apprendre pour avancer) ; cartographier plus souvent ; **burn-down des risques** à côté du burn-down des fonctions ; la largeur et la profondeur donnent la taille, le nombre de chemins la complexité.
- Da Vinci : la stratégie incrémentale pure (brique par brique) suppose une vision exacte ; l'artiste esquisse d'abord toute la composition puis étoffe et affine. **Itératif ET incrémental** : itérer = évaluer et changer ce qui est fait (le changement est le résultat normal de l'apprentissage, pas un échec ni un « scope creep ») ; incrémenter = ajouter.
- **Ouverture / milieu / fin de partie** : ouverture = fonctions ou étapes essentielles traversant tout le produit, le techniquement risqué, sans options ni règles métier sophistiquées ; milieu = compléter, options, règles difficiles, tester performance, montée en charge, utilisabilité ; fin = affiner, rendre efficace, retours des utilisateurs. **C'est l'équipe qui tranche cette stratégie** (elle voit les risques).
- Risques : Eric = risque de mauvais produit (releases complètes aux clients) ; Mike et Aaron = risque technique (tranches internes) ; mettre le risqué en premier même au sein d'une release.
- Ch. 5 (exercice de la matinée) : **tâches utilisateur** = phrases verbales courtes, briques de base de la carte ; les gens diffèrent (contextes) ; **niveaux de but** de Cockburn (niveau de la mer = tâche qu'on termine avant de s'interrompre ; sous-tâches ; tâches de synthèse) pour agréger ou décomposer.
- Flux narratif gauche → droite ; voir ce qui manque ; **alternatives, variations, exceptions** (et le matin idéal) remplissent le corps ; colonnes pour les tâches semblables ; les désaccords sur l'ordre signalent souvent que l'ordre n'importe pas.
- **Activités** = groupes de tâches vers un but commun ; activités et tâches hautes = **backbone** ; nommer les activités avec les mots des utilisateurs.
- **Tranche pour un outcome** : objectif à gauche (« sortir en quelques minutes ») ; garder l'activité vide pour montrer qu'on ne l'atteint pas ; ajouter les tâches propres à ce cas ; le flux reste stable selon les objectifs.
- Encadré Reading Plus : brise-glace « pourquoi avez-vous fait cela ? » qui installe la question de la valeur.
- **Carte « maintenant » vs carte « plus tard »** : la carte actuelle (journey map) s'enrichit de douleurs, joies, questions, idées.
- Tomax : demander aux décoratrices d'écrire tout ce qu'elles ont fait la dernière fois qu'elles ont vendu des stores.
## Tranche 6 (ch. 5 fin, ch. 6, ch. 7 début)
- « Avec le logiciel c'est plus dur » : arrêter de parler fonctions et écrans ; si on ne connaît pas l'utilisateur, la carte révèle surtout ce qu'on ignore → aller apprendre, ou cartographier **avec** eux.
- **Six étapes** : 1) cadrer le problème (pour qui, pourquoi) ; 2) carte de la vue d'ensemble, large et peu profonde (au besoin le monde actuel avec douleurs et joies) ; 3) explorer (autres utilisateurs, alternatives, ce qui va mal ; esquisser, prototyper, tester) ; 4) **stratégie de release** ; 5) **stratégie d'apprentissage** (expériences MVP) ; 6) **stratégie de développement** (ce qu'on construit tôt pour voir les risques techniques).
- Encadré SAP : coach, atelier d'un jour ; vision (elevator pitch, Cover Story) ; personas issus de la recherche ou hypothèses à tester ; trois niveaux (étapes d'usage → activités par rôle → stories « en tant que ») ; couleurs par persona ; **« taches blanches », questions, dépendances, trous mis sur la carte** avec d'autres couleurs ; priorisation par vote, Kano simplifié (must-haves, delighters, satisfiers) ; estimations détaillées hors atelier ; passage à l'échelle par formation de coaches.
- Ch. 6 : documents → chacun imagine autre chose ; « bad requirements » ; décrivent le quoi sans le pourquoi ; **meilleures solutions = collaboration entre ceux qui ont le problème et ceux qui peuvent le résoudre**. Kent Beck : raconter avant que le logiciel le fasse ; on le fait bien si cela génère énergie, intérêt et vision. Sans discussion riche, on n'utilise pas vraiment des stories.
- **3 C** (Ron Jeffries) : Card, Conversation, Confirmation. Confirmation = qu'allons-nous vérifier pour savoir que c'est fini (critères d'acceptation, story tests) ; comment le démontrerons-nous en revue (révèle des trous : données réalistes).
- Conversation : objectif commun = comprendre le problème et le résoudre au mieux, puis s'accorder sur quoi construire. Mots et images (personas, workflows, croquis d'IHM) ; photos ; critères d'acceptation visibles pendant la conversation.
- Ch. 7 : « user » ajouté pour garder la perspective extérieure. **Template Connextra** (en tant que / je veux / afin de) né du besoin de retrouver qui et pourquoi ; garder des titres courts ; template = démarreur de conversation ; dans une carte, on lit la tâche + le persona au-dessus + l'activité au-dessus pour reconstituer la phrase.
- Encadré ThoughtWorks : grandes réunions de planification = « accident » ; mieux : petites conversations ciblées (affinage en petit groupe en semaine 1, paire développeur + analyste ~20 min par story), puis affinage collectif fluide ; tailles de stories plus homogènes.
- **Template zombies** ; le template est un « chasse-neige » d'apprentissage, pas une bonne pratique ; pas besoin du template pour qu'une story soit une story. Préférence : titre court + Qui / Quoi / Pourquoi avec de la place pour noter.
- **Check-list de conversation** : vraiment parler du **qui** (types d'utilisateurs, clients/acheteurs, autres parties prenantes) ; du **quoi** (tâches, mais aussi services techniques sans perdre qui et pourquoi) ; du **pourquoi** (en couches, « bâton du pourquoi ») ; de **ce qui se passe hors du logiciel** (où, quand, combien de fois, qui d'autre) ; de **ce qui va mal** ; des **questions et hypothèses** (qui fait le travail pour y répondre ; hypothèses utilisateurs et techniques ; plan pour apprendre) ; de **meilleures solutions**.
## Tranche 7 (ch. 7 fin, ch. 8, ch. 9, ch. 10 début)
- Check-list suite : parler du **comment** (sans comment, impossible de penser au coût ; respecter l'expertise des autres ; le problème est de prendre une solution pour une exigence) ; parler de **combien de temps** (« un prix pour décider » ; comparaison avec l'existant ; estimations, pas engagements).
- Photos de vacances : noter les décisions, questions, hypothèses ; noter qui était dans la conversation ; photographier ; extraire plus tard.
- Ch. 8 : beaucoup de rôles (PO, BA, testeur, designer UI, rédacteur technique, chef de projet) → **beaucoup de conversations différentes par story**, certaines avant d'autres, certaines répétées.
- La carte est une **fiche de catalogue de bibliothèque** : un jeton qui renvoie vers une information qui grossit à chaque conversation (wiki, outil, tableaux de papier). Encadré Atlassian : murs + outils (Confluence : photos, vidéos, discussions ; tickets référencés sur les post-it).
- **Radiateurs d'information** (Cockburn) vs « glacières » (outils où l'information se fige).
- Contenu d'une carte : **titre court** (le plus précieux ; le réécrire s'il prête à confusion), description qui/quoi/pourquoi ; puis numéro (ne pas désigner les stories par leur numéro), estimation/taille/budget, valeur, **métriques** de succès après release, dépendances, statut, dates ; critères au dos. Seul le titre est obligatoire.
- Outils : construire la compréhension partagée → mur, ou outils où tous voient et réorganisent en même temps (caméra de document en visio) ; se souvenir → wiki avec photos et vidéos ; **suivre** → outils (diagramme de flux cumulé) : ne pas utiliser un outil de suivi pour construire la compréhension partagée.
- Ch. 9 : cycle complet carte → conversation → confirmation → construction → revue → apprentissage. **Remettre tous les détails à quelqu'un d'autre pour qu'il construise ne marche pas** (ce sont vos photos de vacances). **Tradition orale** : celui qui connaît reraconte à la personne suivante, qui pose des questions et se fait ses propres photos.
- Anti-pattern : tout le monde dans toutes les conversations (« trop de réunions ») ; groupes de **2 à 5** pour décider, puis partager.
- **Inspecter** : revue de fin de sprint au-delà de la démo ; trois qualités : **expérience utilisateur, fonctionnelle, code** (dette technique). Séparer : a-t-on construit ce qui était convenu ? puis, maintenant qu'on le voit, faut-il changer ? → nouvelles cartes.
- **Ce n'est pas pour vous** : tester avec de vrais utilisateurs accomplissant un vrai but, au moins toutes les deux semaines ; pas tout le monde à la fois ; empathie ; chaque problème → une carte.
- Cockburn : pour chaque story, en mettre trois (la story, « corriger la première », « corriger la deuxième »). Dans un processus agile, **l'apprentissage est le but** ; prévoir d'avoir souvent tort.
- Beck (2011) : « apprentissage validé plutôt que logiciel qui fonctionne » ; utiliser des stories pour piloter aussi prototypes, entretiens, observations.
- Ch. 10 : gâteau de Sydnie : la conversation porte sur qui, pourquoi, contexte, options faisables ; le **plan de travail** (tâches de développement, de test, de design, de rédaction) est fait **par l'équipe**, pas pendant la conversation ; on raconte des stories sur le logiciel final, pas sur les ingrédients.
## Tranche 8 (ch. 10 fin, ch. 11, ch. 12 début)
- Story trop chère → revenir au problème, chercher une autre solution. Grosse mais abordable → la découper quand même pour voir et mesurer plus tôt. **Ne pas découper par couches techniques** (semaines d'interface puis de logique) : « petits gâteaux » livrables qui permettent de goûter (une tâche utilisateur évaluable, ou un risque technique exposé). « Un demi-gâteau cuit, pas un gâteau à moitié cuit » (Hohman).
- Ch. 11 : **trois bonnes tailles** : pour l'utilisateur = satisfait un besoin ; pour l'équipe = **quelques jours** à construire et tester ; pour l'entreprise = atteint un outcome métier (la release). La bonne taille = celle qui sert la conversation en cours ; on « remonte » le niveau selon l'interlocuteur.
- Stories = rochers (rester une story à toute taille) ; **l'outil pour casser = la conversation** ; ne pas être trop précis sur la taxonomie ; **épopée** = grande story qu'on sait devoir découper (ne pas s'en servir comme bâton) ; la garder pour en parler ; **thème** = sac de stories liées (release, fonctionnalité, type d'utilisateur).
- **Cycle de vie (rock breaking)** :
  1. **Opportunités** (backlog d'opportunités) : discussion qui/quoi/pourquoi de haut niveau → décision **aller plus loin / jeter** ; célébrer ce qu'on jette.
  2. **Découverte** d'une solution minimale viable : qui, comment ils font aujourd'hui, ce qui change, à quoi ressemble la solution, combien de temps ; valider les hypothèses (règles métier, réglementation, terrain, prototypes d'IHM, **prototypes techniques**) ; **spikes** décrits comme des stories ; résultat = **backlog de release**.
  3. **Livraison** : **ateliers de stories** (« dernières meilleures conversations ») avec développeurs et testeurs pour détailler, découper et **convenir des critères d'acceptation** ; pendant le backlog refinement ou la planification ; tailles prêtes pour le sprint.
  4. Continuer à parler pendant la construction (daily ; aller voir les développeurs).
  5. **Évaluer chaque morceau** : qualité, planification (fini ce qu'on prévoyait ? plus long ?), façon de travailler → **sprint review et rétrospective**.
  6. Évaluer avec utilisateurs et clients quand il y a « assez » (un écran ou un flux permettant une tâche).
  7. Évaluer avec les parties prenantes : progression vers la **solution minimale viable**, pas vers les petits morceaux ; partager les tests utilisateurs.
  8. **Release** quand il y a « assez » pour l'outcome ; puis **métriques et conversations** pour vérifier que les outcomes sont atteints ; les opportunités trouvées repartent au début. Un produit commence à vivre quand il est livré.
- Ch. 12 : un seul product owner pour toutes les stories et conversations ne marche pas (goulot ; manque d'expertises). Mais pas de design par comité : le PO décide (« design by community is not design by committee »).
- **Valuable–usable–feasible** (Cagan) → **équipe de découverte** de 2 à 4 (« triade ») : PO (vision, marché), UX (utilisateurs, prototypes), **ingénieur senior** (architecture ; souvent la source des solutions les plus innovantes) ; elle coordonne parties prenantes, experts, clients, utilisateurs ; le leader aide chacun à prendre possession.
- **Three amigos** à l'atelier de story : développeur (idéalement celui qui codera), **testeur** (meilleur au What-About), membre de l'équipe de découverte (UX ou BA) ; ils conviennent des critères d'acceptation, produisent la meilleure estimation et découpent en stories de **1 à 3 jours**.
- Anti-pattern client–fournisseur : le client sait et explique (« exigences »), le fournisseur estime (= s'engage).
## Tranche 9 (ch. 12 fin, ch. 13, ch. 14 début)
- Anti-pattern client–fournisseur : le client comprend mieux son problème qu'il ne prédit sa solution ; le technicien est souvent le plus qualifié pour résoudre ; viser la relation **médecin–patient** (« dites-moi où ça fait mal ») plutôt que serveur–client.
- En contexte DSI : le **BA comme producteur de musique** (aide les parties prenantes à réussir, quitte à dire ce qu'elles ne veulent pas entendre) plutôt que preneur de commandes ; faire porter le rôle de PO au métier est risqué sans aide ni temps.
- « Story » désigne à la fois la carte, le morceau de logiciel et la conversation.
- Ch. 13 : **opportunité** = « rocher zéro » ; conversation : **pour qui ; quels problèmes** (et comment ils les résolvent aujourd'hui) ; **ce qu'on imagine** ; **pourquoi** (bénéfice pour l'organisation, alignement sur la stratégie ; pas de ROI à ce stade) ; **taille** (estimation au jugé par comparaison : jours, semaines, mois). **Backlog d'opportunités.**
- Issues : **aller plus loin** (= découverte, pas construire), **jeter** (« no-go est un excellent résultat » ; associer ceux qui portaient l'idée), **manque d'information** (liste de ce qu'il faut apprendre), ou remettre à plus tard.
- **Opportunity Canvas** (inspiré de Cagan et du Business Model Canvas) : 1) problèmes ou solutions, 2) utilisateurs et clients (ne pas viser « tout le monde »), 3) solutions aujourd'hui, 4) valeur utilisateur, 5) **métriques utilisateur**, 6) stratégie d'adoption, 7) problème métier, 8) **métriques métier**, 9) budget. Lecture gauche→droite = maintenant→plus tard ; haut→bas = besoins utilisateurs→besoins de l'entreprise. Pas un formulaire ; la décision revient au PO.
- « Opportunité » ne doit pas être un euphémisme : même si c'est « go » d'office (roadmap imposée), tenir la conversation de cadrage ; si les décideurs sont absents, poser des hypothèses et les leur soumettre.
- Pas de story map pour gérer les opportunités, mais une **carte « maintenant »** (journey map) du produit actuel pour situer les opportunités : **points chauds** ; prioriser celles qui touchent des activités fréquentes d'utilisateurs critiques ; ajouter plaintes et joies ; une zone de douleur sans opportunité en appelle une.
- Encadré Atlassian : journey map multiproduits, sous-groupes, douleurs/opportunités/hypothèses, concepts votés (faisabilité, viabilité, désirabilité), BD de 20 pages.
- Encadré « remapping par répétition » : jeu de rôles par personas avec un but, observateurs, on reconstruit la carte avec les acteurs, douleurs et gains → hypothèses cassées.
- **Être sélectif** : jeter agressivement avec les parties prenantes.
- Ch. 14 : un backlog actionnable ne se « capture » pas, il se découvre. Découverte = apprendre (problèmes ? valeur ? utilisable ? faisable ?) ; **si on ne produit que des stories, on s'y prend mal** (créer d'autres modèles simples).
- **Quatre étapes** : 1) **cadrer** (borner ; permet d'arrêter les discussions hors cible) ; 2) **comprendre clients et utilisateurs** : personas légers construits ensemble à partir de faits (dire honnêtement la part de suppositions ; les beaux documents de personas ne sont pas lus) ; **profils d'organisation** (orgzonas) pour les produits achetés par des organisations ; **carte narrative du fonctionnement actuel** (faits, observations, douleurs, joies, points chauds) ; 3) **imaginer la solution** : story map de la vie de l'utilisateur avec la solution (trois niveaux si long) ; **visualiser l'IHM** (storyboard d'écrans au-dessus de la carte) car les mots seuls ne suffisent pas ; 4) minimiser et planifier.
## Tranche 10 (ch. 14 fin, ch. 15 début)
- Encadré Seiden : des milliers de stories classées par **module fonctionnel** → incompréhensible ; une carte centrée sur l'**usage** (colonne vertébrale en affiches) permet des releases transverses aux modules ; storyboards dessinés.
- **Design Studio** (8 à 12 personnes) : décrire le problème (cadrage, personas, carte actuelle), inspirations, tout le monde esquisse (≈15 min), partage en groupes de 4 avec retours sur l'adéquation au problème, consolidation par groupe, partage ; ensuite l'équipe de découverte tranche (pas de comité). Visualiser la solution fait trouver des manques dans la carte.
- **Valider la complétude** : le cerveau saute les étapes entre les scènes d'action ; la carte en largeur rappelle mise en place, rapports, notifications, administrateurs, managers.
- **Valider les contraintes d'ingénierie** : présenter la carte aux ingénieurs et architectes tôt (contraintes, alternatives équivalentes moins coûteuses) ; ex. moteur de règles à changer, repéré devant la carte.
- **What-About sous l'interface** : règles métier difficiles, validations de données, systèmes et services back-end ; les ajouter comme stories ou notes ; faire relire largement.
- Métaphore du film : scénario + storyboard + lieux, décors, effets → plan grossier et estimation → budget et calendrier, **avant** de construire.
- Encadré Hussman : idée → passagers → **exemples** du simple au complexe (« remplacez exemple par test ») → parcours ; choisir les parcours qui apprennent le plus ; construire un parcours à la fois et l'observer ; « arrogance produit ».
- Ne pas célébrer quand « les exigences sont finies » (pire : un long document d'exigences qui brouille tout).
- **4) Minimiser et planifier** : **si on ne jette pas plus d'idées qu'on n'en garde, on fait mal la découverte** ; viable = réussi pour une stratégie, des clients et des utilisateurs précis ; repenser les releases suivantes après la première, le monde ayant changé.
- **Secret de la priorisation** : remplacer « valeur métier » par quelque chose de précis : **objectifs métier précis → utilisateurs → leurs buts et activités → fonctionnalités**. Prioriser les fonctionnalités d'abord est l'erreur courante.
- Tableau d'activités de découverte : cadrer (problèmes métier nommés, métriques métier, listes d'utilisateurs, métriques d'usage, grands risques et hypothèses) ; comprendre (rôles, profils, orgzonas, cartes actuelles, recherche) ; imaginer (story maps, cas d'utilisation, scénarios, croquis et storyboards, prototypes d'IHM, **esquisses et prototypes d'architecture**) ; minimiser et planifier (cartes tranchées, **estimation pour fixer un budget**, plan de développement qui minimise les risques).
- Ch. 15 : tout est hypothèse jusqu'à l'observation après livraison. ~20 % de succès, ~20 % d'échecs, ~60 % sans effet (Standish : 64 à 75 % des fonctionnalités rarement ou jamais utilisées).
- Design thinking (IDEO, d.school) : **empathie** (aller voir, travailler à côté ; données ≠ empathie) ; **définir** (cartes actuelles, douleurs, personas ; choisir précisément des problèmes) ; **idéation** (plusieurs solutions, idées posées dans la carte) ; **prototyper** (papier) ; **tester** (les utilisateurs accomplissent une vraie tâche ; pas une démo ni de la vente). Équipes pluridisciplinaires, modèles simples.
- Façons de rater : pas de cadrage métier ; recherche sans fin (time-box) ; pas de contact utilisateur ; trop de problèmes à la fois ; seuls les designers proposent ; une seule idée ; prototype joli mais inutilisable ; croire que le processus garantit le succès ; ignorer le coût ; chercher un coupable.
## Tranche 11 (ch. 15 fin, ch. 16 début)
- Ries : build–measure–learn ; réduire la durée du cycle (jours, pas mois) pour ne pas s'attacher aux solutions ; Lean Startup utile hors startups (toujours du risque).
- **Commencer par deviner** (passion, expérience, intuition) ; personas et cartes actuelles en heures ou jours, avec des gens qui connaissent le terrain ; plusieurs solutions, converger vite.
- **Nommer ses hypothèses risquées** (utilisateurs, solution, techniques) → choisir les plus grosses.
- **Concevoir le plus petit test** : JSTOR : liste d'hypothèses sur les étudiants et sur la solution ; **design comic** + entretiens ; prototype de code seulement pour les risques d'utilisabilité et techniques, après.
- **Mesurer** (entretiens, interceptions, analytics) ; **repenser** solution et hypothèses ; célébrer d'avoir eu tort tôt ; « ne pas apprendre est souvent le plus grand échec ».
- Stories en découverte : même façon de travailler mais plus vite et moins formel (prototypes en heures ; on s'attend à ce que la plupart des idées échouent).
- Ch. 16 : release backlog segmenté en début (apprendre) / milieu (étoffer) / fin (affiner) ; viennent les **« dernières meilleures conversations »**.
- **Atelier de story** (recette) : annoncer les stories à l'avance, **participation volontaire** ; 3 à 5 personnes : quelqu'un qui comprend les utilisateurs et l'IHM (PO, UX, BA), un ou deux **développeurs qui connaissent le code**, un **testeur** ; si une préoccupation manque, suspendre. Approfondir : exactement qui, comment il l'utilise, à quoi ça ressemble, **comment le logiciel se comporte sous l'interface (règles métier, validations)**, **à peu près comment on le construira** (pour prédire la durée). Rien n'est absolument requis : si c'est cher, revenir au problème. **Convenir** : que vérifierons-nous pour dire que c'est fini ? comment le démontrerons-nous en revue ? Talk and doc, **parler en exemples** (données saisies, réponses vues), **découper et amincir**. Ça ne marche pas quand une seule personne parle, quand on ne fait que des critères d'acceptation sans raconter qui fait quoi et pourquoi, quand on n'envisage pas d'options.
- Mieux vaut des ateliers avant la planification que de longues réunions de planification (on accepte tout pour en sortir). Encadré RAC : narrations de 1 à 5 pages projetées = équipe désengagée ; après rétrospective : abandon des narrations, élaboration avec métier et équipe autour de modèles visuels, cadence fixée ; la BA devient facilitatrice.
- **Les foules ne collaborent pas** : participation volontaire ; **fishbowl** (3 à 5 au tableau, un entrant = un sortant).
- **Découper et amincir** : l'exemple du chapitre : les critères d'acceptation révèlent le découpage en versions successives (brouillon, illustrations, index…) ; inspecter en route.
- **Good–Better–Best** : bon (à peine suffisant), mieux, meilleur ; faire le basique sur toute l'application avant d'améliorer : plus sûr pour tenir les délais.
- Sortie d'un atelier : stories de bonne taille + modèles + critères d'acceptation ; parfois plusieurs ateliers et un peu de recherche.
- **Recette de planification de cycle** : préparer — choisir les stories un ou deux cycles à l'avance avec l'équipe produit ; ateliers en amont ; inviter l'équipe et ceux dont on aura besoin. Planifier — commencer par le **grand objectif du cycle** et comment ces stories font avancer la solution ; revue rapide des stories avec mots et images ; **time-box pour que l'équipe de livraison planifie seule**…
## Tranche 12 (ch. 16 fin, ch. 17, ch. 18 début)
- Planification (suite) : l'équipe planifie seule en petits groupes (trois amigos) une recette par story pendant ~1 h, PO/UX/BA à proximité ; **décide combien de stories elle peut finir**, en tenant compte des congés ; partage le plan ; si ça ne rentre pas, ramener une story de « mieux » à « suffisant » ; l'accord doit être pris au sérieux pour être fiable et prévisible ; célébrer.
- **Utiliser la carte pendant la livraison** : donner la vue d'ensemble à l'équipe (meilleures décisions tactiques) ; **visualiser l'avancement** (retirer ce qui est en cours ou marquer ce qui est fini) ; choisir les prochaines stories en regardant la carte comme un peintre ; **mini-cartes en atelier** avec les critères d'acceptation en post-it.
- Encadré campagne Obama : mur de stories gauche→droite par **semaine calendaire**, haut→bas par priorité, couleurs par activité ; ajout des stories avec les dirigeants, sur le problème réel ; le développeur travaille directement avec la partie prenante qui sait le plus ; le MVP en Iowa a déçu, la confiance est venue des améliorations hebdomadaires visibles.
- Ch. 17 : **ne pas tout découper d'un coup** (Asteroids) : découper **progressivement et juste à temps**, avec un but à chaque étape : 1) opportunités (pour qui, problèmes, stratégie ; scinder les opportunités enflées) ; 2) découverte (valuable-usable-feasible ; ne passer que le minimum au release backlog) ; 3) stratégie de développement (casser en vue d'apprendre, risques d'adoption et techniques) ; 4) planification du cycle (une story peut correspondre à **un seul accord / critère**).
- **Regrouper les petites stories** : imprimer, regrouper en silence, chacun peut déplacer, donner un titre de synthèse précis (« améliorer la saisie des commentaires » plutôt que « améliorations IHM »), les petites deviennent des puces ; renvoyer au release backlog ou au backlog d'opportunités ; regrouper aussi les bugs mineurs avec les majeurs de la même zone.
- **Ne pas trop cartographier** : un peu avant et un peu après la fonctionnalité ; « si on n'a pas besoin d'en discuter, pas besoin de le cartographier ».
- **Petites choses évidentes** après livraison (bugs, petites améliorations) : directement au release backlog et en atelier, sans découverte ; Atlassian compte ses petites corrections.
- Ch. 18 : **revue d'équipe** d'abord, entre ceux qui ont construit (lieu sûr ; sans les parties prenantes) : **produit** — tout essayer ; noter de 1 à 5 la qualité UX, fonctionnelle et du code ; écrire des stories pour les défauts ; revoir aussi le travail de découverte ; **plan** — décider ce qui est fini (construit une **définition du fini** commune), **vélocité** = nombre de stories finies, **reste commencé non fini (« overhang »)**, temps de découverte budgété vs consommé ; **processus** — garder ou abandonner les changements essayés, en essayer peu de nouveaux (rétrospective).
- **Revue avec les parties prenantes** : tout le monde ; revoir le **travail de découverte** (opportunités, outcomes attendus, prototypes, retours clients : « seul un fait froid bat l'opinion d'un dirigeant ») puis la **livraison par solution** (cible, outcomes, ce qui est construit, pourquoi c'est incomplet, **progression vers la release**, ce qui reste) ; réorienter les suggestions hors de l'outcome visé.
- **« Assez »** : différent pour parties prenantes, clients, utilisateurs ; balance de briques LEGO.
- **Apprendre des utilisateurs** : test, pas « show and tell ».
- **Apprendre de la release** : décider pour chaque release **comment mesurer** (métriques intégrées au produit) et **quand observer** les utilisateurs ; les plaintes sont des indicateurs retardés ; écrire des stories ou alimenter le backlog d'opportunités.
- Releases à date fixe : ouverture/milieu/fin ; **le logiciel n'est jamais fini**.
## Tranche 13 (ch. 18 fin, épilogue, références ; l'index n'apporte rien de plus)
- **Les outcomes ne sont jamais assurés** ; prévoir d'apprendre et de changer après chaque release ; **les améliorations après release sont les plus précieuses**.
- **Évaluer la maturité de release avec la carte** : pour chaque activité majeure, « si on livrait maintenant, quelle note ? » → bulletin (A, A–, B+, D, B+) ; concentrer les dernières semaines sur l'activité notée D.
- Épilogue : « un grand art n'est jamais fini, seulement abandonné ».
